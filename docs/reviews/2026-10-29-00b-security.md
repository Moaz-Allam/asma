## Confirmed vulnerabilities

- `D:/work/web/asma/lib/observability/alert.ts:35-40` + `D:/work/web/asma/lib/observability/client.ts:29` - **[Medium]** Anyone can forge or flood the money-safety alerts. An alert is recognised only by data the sender sets (`scope.setTag('alert', reason)`, `scope.setFingerprint(['alert', reason, detail.recordId])`). The server sends it with the same DSN the browser bundle ships (`const DSN = process.env.NEXT_PUBLIC_SENTRY_DSN`). The D80 rules match only tag `alert` plus environment `production`, and the sender chooses both. **Exploit:** anyone copies the DSN from the page and posts events tagged `alert:flag_read_failed` in `production`, with a new `recordId` each time. Each one opens a new issue, so the owner gets a fake kill-switch email per event. Or the attacker uses up the 5k monthly error quota and spike protection (D81), and the next real `raiseAlert` is dropped. - Send server errors and alerts through a server-only DSN in a separate Sentry project (not `NEXT_PUBLIC_`), and point the alert rules at that project only. Set a per-key rate limit on the browser DSN. Keep the outbox email (13) as an independent channel for money alerts. Do this before 08.
- `D:/work/web/asma/next.config.ts:52-57,81` (generated by `D:/work/web/asma/node_modules/@sentry/nextjs/build/cjs/config/withSentryConfig/tunnel.js:22-69`) - **[Low]** Both telemetry paths are open relays.
  - The tunnel takes org, project and region from the query: `o=(?<orgid>\d*)`, `p=(?<projectid>\d*)`, `r=(?<region>[a-z]{2})` go to `https://o:orgid.ingest.:region.sentry.io/api/:projectid/envelope/`.
  - `/api/a/:path*` reaches any `eu.i.posthog.com` path, for any project token.
  - **Exploit:** anyone pushes envelopes to their own Sentry org (US or EU), or events to their own PostHog project, through our domain and on our Vercel quota. An injected script gets an exfiltration path that `connect-src 'self'` allows.
  - `/api/a/array/<any token>/config.js` also serves JS built from another project's settings on our origin. CSP2-only browsers trust that through `'self'`.
  - Fix: replace the rewrites with Route Handlers. Allow only our org, project and `r=de`, our `phc_` token, a fixed list of PostHog endpoints and methods, a body size cap, and a request-header allow list. Add a Vercel firewall rate limit on `/api/e` and `/api/a/*`.

## Likely issues

- `D:/work/web/asma/next.config.ts:52-57` + `D:/work/web/asma/lib/security/headers.ts:13` + `D:/work/web/asma/node_modules/posthog-js/lib/src/request.js:361-371` + `D:/work/web/asma/node_modules/next/dist/server/lib/router-utils/proxy-request.js:30-39` - **[High once 01 sets `sb-<ref>-auth-token`; Medium today]** The rewrites forward the browser's request headers to PostHog and Sentry unchanged.
  - That includes every first-party cookie. On previews it may also include the `_vercel_jwt` protection cookie.
  - posthog-js calls `fetch` with no `referrerPolicy`, and our `strict-origin-when-cross-origin` policy sends the full URL on same-origin requests. So the `Referer` carries the raw page URL (`?token=`, `?email=`, `?code=`) to PostHog without passing the scrubber. Sentry's own transport uses `referrerPolicy: 'strict-origin'`, so it is not affected.
  - Header forwarding is confirmed for `next start` (httpxy forwards `req.headers`). To confirm the rest:
    - In the e2e stub, assert that `route.request().allHeaders()` has no `cookie` and no query in `referer`. This fails today for the `?token=e2e-secret-token` journey.
    - Read the upstream headers from a throwaway preview.
  - Fix: use the Route Handlers above and drop `cookie`, `referer` and `authorization`.
  - Until then: set `Referrer-Policy: strict-origin` (or `no-referrer`); set PostHog `fetch_options: { credentials: 'omit', referrerPolicy: 'no-referrer' }` (sendBeacon still sends both, so this is partial); set Sentry `transportOptions.fetchOptions.credentials: 'omit'`.
  - 01 should not ship until this is fixed.
- `D:/work/web/asma/lib/observability/scrub.ts:426-445` + `D:/work/web/asma/lib/observability/client.ts:72-81` - **[High before the reveal page]** Replay DOM snapshots (rrweb types 2 and 3) leave the scrubber untouched (`return recordingEvent;`). Sentry masks only `maskAttributes = ["title", "placeholder", "aria-label"]` (`D:/work/web/asma/node_modules/@sentry/replay/build/npm/cjs/index.js:8180`). So `href="tel:+90…"`, `mailto:`, map links holding an address, `data-*` and `<option value>` leave in every on-error replay. Running the scrubber returned a type 2 event with `href:"tel:+905551234567"` unchanged. - Add `maskAttributes` (`href`, `src`, `value`, `alt`). Add a `data-pii` container convention with `block: ['[data-pii]']`. Scrub URL, `tel:` and `mailto:` attribute values in types 2 and 3. The reveal position should not start until this is in.
- `D:/work/web/asma/lib/security/csp.ts:55,60-63` + `D:/work/web/asma/proxy.ts:53-54` - **[Medium]** CSP violation reports go from the browser straight to `https://o….ingest.de.sentry.io/api/<p>/security/?sentry_key=…`, never through the SDK or `scrub.ts`. Per CSP3 they carry `document-uri` and `referrer` with the query string. Extensions that inject scripts trigger them all the time, so `?email=` and `?code=` reach Sentry raw. To confirm, trigger a violation on `/tr?email=a@b.co&code=x` on the preview and read the stored `csp` event. - Send reports to a same-origin handler that runs `scrubUrl` and forwards through the door, or drop reporting. At minimum, add `code`, `q`, `ref`, `customer`, `token_hash`, `email` and `phone` to Sentry's server-side scrubbing, and check that it covers `csp.document_uri`.
- `D:/work/web/asma/lib/observability/client.ts:40-59` + `D:/work/web/asma/lib/observability/server.ts:36-51` - **[Medium, latent]** Neither init sets `beforeSendSpan`.
  - INP spans are on by default and are standalone (`D:/work/web/asma/node_modules/@sentry/browser-utils/build/cjs/metrics/utils.js:66`: `standalone: true`).
  - Standalone spans are sent via `createSpanEnvelope` (`D:/work/web/asma/node_modules/@sentry/core/build/cjs/envelope.js:60-71`), which applies only `beforeSendSpan`. They skip `beforeSend` and `beforeSendTransaction`.
  - Their name is `htmlTreeAsString(entry.target)` (`inp.js:74`), which includes `aria-label`, `title`, `alt` and `name` values. A click on a button labelled with a customer's name goes out unscrubbed.
  - Fix: wire `beforeSendSpan` to `scrubSpan`, plus `redactMessage` on the span name, in both inits.
- `D:/work/web/asma/lib/observability/scrub.ts:196-203,330,350` - **[Medium]** Text such as messages and console arguments only has emails, IPs and phones redacted. Any URL inside that text keeps `code`, `token`, `token_hash`, `q`, `ref` and `customer`, which breaks AC-3. - `D:/work/web/asma/lib/observability/scrub.ts:352-361` - **[Medium]** Frame `filename` and `abs_path` are never scrubbed. Sentry fills a stackless error's frame with `getLocationHref()` (`D:/work/web/asma/node_modules/@sentry/browser/build/npm/cjs/prod/integrations/globalhandlers.js:112`), which is the full URL including query and fragment. The scrubber kept `…?code=SECRET1#access_token=SECRET2`. - Run `scrubUrl` on http(s) frame paths.
- `D:/work/web/asma/lib/observability/scrub.ts:389-391,338` - **[Low]** The transaction is scrubbed only when `event.transaction.startsWith('/')`. But `D:/work/web/asma/node_modules/@sentry/nextjs/build/cjs/server/enhanceHandleRequestRootSpan.js:40-42` renames `GET /_error` to `${method} ${target}`, and `http.target` keeps the query. - `D:/work/web/asma/lib/observability/scrub.ts:165-180` - **[Low]** The `url.fragment` and `http.fragment` attributes (set at `D:/work/web/asma/node_modules/@sentry/core/build/cjs/utils/url.js:72` and `fetch.js:214`) are not recognised as URL keys, so `#access_token=…` survived. - `D:/work/web/asma/lib/observability/scrub.ts:152-159,100-117` - **[Medium, latent]** Three gaps in what the scrubber treats as personal:

## Checked and sound

- **Migration and pgTAP 03:** the migration revokes everything, then grants exactly:
  - `table_privs_are` pins the grants.
  - anon gets 42501 on `platform_settings`.
  - A non-admin update is a no-op; the admin update works.
  - Writes are gated on `app_metadata.role`, which users cannot edit.
  - The `_enabled` CHECK is tested both ways; KSA is inactive with all flags `false`.
  - `health_ping()` is security invoker with `search_path=''`, reads nothing, has PUBLIC revoked, and is allow-listed in test 02.
- **`isEnabled`** fails closed on error, timeout, abort, missing row, non-boolean and throw, and never throws.
- **Deployment gate:**
  - `APP_LOCAL_ONLY` with `VERCEL=1` throws at both build and boot, and zod accepts only `'1'`.
  - The DSN must be an EU SaaS DSN with no secret, port or query.
  - The PostHog key must be `phc_`.
  - Error messages name variables, never values.
  - The browser gets only `NEXT_PUBLIC_APP_ENV` and `NEXT_PUBLIC_APP_RELEASE`.
- **Source maps:** disabled off deployments; on deployments they are uploaded and then deleted, a failed upload fails the build, and the post-build check runs on Vercel.
- **Secrets:** no real key in tracked files. `.gitleaksignore` holds two exact fingerprints whose values are fake (checked with `git show`). `.env.sentry-build-plugin` is gitignored.
- **Sentry options:**
  - `sendDefaultPii` and `includeLocalVariables` are off, and `tracePropagationTargets` is empty on both sides.
  - `user` is deleted.
  - `request` is cut to method, URL, query and allow-listed headers, even when the SDK's internal copy of the request holds cookies or a body.
  - The scrubber fails closed, and the transport sends the origin only as `Referer`.
- **`onRequestError`:** the header allow list excludes cookie, authorization, forwarded-for and IP headers, and the path is scrubbed before `contexts.nextjs.request_path`. That is the only place the SDK sets that context.
- **PostHog:**
  - Cookieless, memory persistence, never identifies anyone, every automatic feature off.
  - Remote config and external scripts are disabled (`remote-config.js` `_shouldDisableFlags`, `external-scripts-loader.js:23`), so a project setting cannot switch on console-log capture or recording.
  - Events are allow-listed and typed, and URL properties are scrubbed.
- **CSP:**
  - The nonce is a fresh CSPRNG value per request, set on both the request and the response.
  - `strict-dynamic`, and no `unsafe-eval` in production.
  - `object-src` and `frame-ancestors` are `'none'`; `base-uri` and `form-action` are `'self'`.
  - The report URI is built only from a validated DSN, so no header injection.
  - A malformed DSN or Supabase URL fails at boot (fail closed).
  - Pages are force-dynamic and `no-store`, so a request header set by an attacker cannot poison other users.
  - The static headers cover `/:path*`.
- **Relay destinations:** the tunnel and rewrites can only reach `*.ingest[.xx].sentry.io` and the two PostHog EU hosts (anchored `has` patterns), so there is no SSRF to other hosts. `/api` is outside the proxy matcher, and Turbopack adds no middleware wrapper, so GHSA-mchm-gjx6-7h55's handling never touches `proxy.ts`.
- **Health:** fixed body, no error text, `no-store`, one shared in-flight ping, a stateless anon client. It shows the full SHA and `fra1` by AC-10.
- **Error boundaries** render no error text and report each error once.
- **CI** runs on `pull_request`, has no secrets, and pins gitleaks by checksum.

The reviewer confirmed the scrubber findings by running `scrub.ts` on crafted inputs from two probe scripts in the session scratchpad (outside the repo). Nothing in the repo was changed.

## Recommendation

**fix then ship.** Before merge:
- Stop the header forwarding to PostHog and Sentry (`Referrer-Policy: strict-origin` plus `credentials: 'omit'` at minimum; Route Handler proxies are better and also close the open relays).
- Add `beforeSendSpan`.
- Scrub URLs inside message text, frame paths, `METHOD /path?…` names and `.fragment` keys, so AC-3 holds as written.

Later:
- Move alerts to a server-only DSN before 08.
- Fix replay attribute masking and key matching before the reveal page.
- Add the flag-alert validation before the first flag caller.
