# Review: feat/09-commission-payment (spec 0011-09, D175)

Reviewer: fresh read of the uncommitted working tree against HEAD 826bf0d, on a model that did not write the code, with the slice reviewer checklist (spec coverage, rules that never bend, three locales, logical properties, single doors, tests per layer). Read only: no test, database or e2e command was run, so the pgTAP plan counts (21 plans 107, 22 plans 20) and every test result are unverified here. The security review is a separate file.

Scope read: the migration `20261121090000_commission_payment.sql` in full, `lib/relay` changes, `lib/requests` door, `actions/payments.ts`, the pay, return and receipt pages, `CheckoutWaiter`, `PayButton`, `AgreementLine`, `NextStepPanel`, the request page, the timeline, messages in all three locales (key parity for `Payment` and `Requests` checked by script: 224 keys each, no gaps), and the test files by name and scenario.

## Verdict

No Blocker. One Major (the receipt link is missing in the normal success flow). The money path in Postgres matches the spec and the rules: price never comes from the client, the commission fee and attempt are opened by one definer function under the request lock, `accept_commission` carries R-1, every money change stays inside `apply_fee_paid`, the payer reads only through `my_checkout` and `my_receipt`, and no user path imports `lib/psp` or `lib/relay`.
