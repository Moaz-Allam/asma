# Internationalisation and regions

> **Decided 2026-08-17, replacing "Arabic-first RTL" as a global constant.**
> Three languages — **Arabic (`ar`), Turkish (`tr`), English (`en`)**.
> Two regions — **Turkey (TR)** and **Saudi Arabia (KSA)**.
>
> This resolves blocker B1 and supersedes every "Arabic-first" statement that implied a single
> language or a fixed page direction. The RTL discipline in `ui-rules.md` §3 does **not** relax —
> it becomes load-bearing, because direction is now a runtime value rather than a constant.

---

## 1. What changed, and why it is not just "add translations"

The old model had one language and one direction, so `dir="rtl"` could be hardcoded in the root
layout and every screen tested once. Now:

| Locale | Script | Direction | Notes |
| --- | --- | --- | --- |
| `ar` | Arabic | **RTL** | Arabic-Indic digits are a display choice, never a storage format |
| `tr` | Latin | LTR | Needs `ı İ ş ğ ç ö ü`. **Case conversion is a real hazard — see §6** |
| `en` | Latin | LTR | Fallback locale; also the language of our own logs and identifiers |

**Direction is a function of locale, computed per request.** A layout that assumes either direction is
a bug. This is precisely why the logical-property rule already exists — a codebase written with
`ms/me`, `ps/pe`, `start/end` flips for free; one written with `ml/mr` must be rebuilt.

## 2. Regions — one deployment, `region` column (D14)

Both regions run from **one deployment and one database**, distinguished by a `region` column, for
operational simplicity. **An account belongs to exactly one region** — a person operating in both
markets creates a second, separate account, which is what keeps one currency per account and per
posting group.

| | Turkey | Saudi Arabia |
| --- | --- | --- |
| Currency | `TRY` (kuruş) | `SAR` (halalas) |
| PSP | iyzico Marketplace (D23) | To be chosen before the KSA launch (Q7); mada mandatory |
| Live at launch (2026-11-07) | ✅ (D22) | ❌ switched off until its PSP exists |
| Locales offered | `tr`, `ar`, `en` | `ar`, `en`, `tr` |
| Default locale **at signup** | `tr` | `ar` |
| Tax/invoicing | e-Fatura | **ZATCA e-invoicing** |
| `regions.code` | `TR` | `KSA` |

Consequences to hold on to:
- **A user account does not span regions.** Same person in both markets = two accounts. This is the
  decision that keeps the money model simple: one account → one region → one currency → one balance.
- **The ledger never mixes currencies within a posting group** — true by construction, since a request
  belongs to one region. Global aggregates must still be grouped by `(region, currency)` (G25).
- **Region is a row value, read from the owning record** — the request, the provider. It is never
  passed in by a caller and never a global constant. **Never infer region from locale** — an Arabic
  speaker in Turkey is the core segment, and conflating the two breaks exactly that user.
- PSP and invoicing adapters are selected from `regions.psp_provider` for the row being processed,
  not from an environment variable.
- **Phone numbers carry the region naturally.** A TR account uses a `+90` number, a KSA account a
  `+966` one, so the same person in both markets has a different number in each. Validate the dialling
  code against the account's region at signup — this is what makes "separate accounts" workable under
  phone-based OTP, where one phone maps to one identity. See G27.

## 3. Locale is independent of region, currency, and PII

Three separate axes that are routinely conflated:

```
locale   → what language the UI renders in       (user choice, cookie + profiles.locale)
region   → which PSP, currency, tax regime       (ROW value — profiles.region, requests.region)
currency → derived from the row's region, never from locale
```

`ar` does not mean SAR. `tr` does not mean the user is in Turkey. Money always formats in the
deployment's currency, with the *locale's* number formatting.

## 4. Routing and layout (Next.js 16 App Router)

Verified against next-intl's App Router docs, not from memory.

- Route segment `app/[locale]/...`, with `routing` defined via `defineRouting({locales, defaultLocale})`.
- `generateStaticParams()` returns the locale list so pages stay statically renderable.
- Each locale layout calls `setRequestLocale(locale)` and validates with `hasLocale()` → `notFound()`
  on an unknown locale.
- **`proxy.ts`** handles locale negotiation and redirects. Same rule as always: this is routing/UX
  only, never authorisation. `requireRole()` still runs in every Server Action and Route Handler.
- Root layout sets **both** attributes from the locale:

```tsx
// dir is derived, never hardcoded. Add a locale here and the whole app flips correctly.
const RTL_LOCALES = new Set(['ar']);
export const dirFor = (locale: string) => (RTL_LOCALES.has(locale) ? 'rtl' : 'ltr');

<html lang={locale} dir={dirFor(locale)}>
```

- **Every locale is prefixed** (`localePrefix: 'always'`, D19). There is no unprefixed route.
- `/` is a negotiation endpoint: cookie → `Accept-Language` → `defaultLocale`, then redirect.
- Locale resolution order: explicit URL segment → `localeCookie` → `Accept-Language` → `defaultLocale`.
- A signed-in user's choice persists on `profiles.locale` and wins over the cookie.

## 5. Translatable content lives in the database, not only in message files

This is the part that is easy to miss. Static UI strings go in `messages/{ar,tr,en}.json`. But this
product's most visible text is **admin-authored data**: category names, service names, addon names,
zone names, question labels, help text, select-option labels, notification templates, rejection
reasons.

`architecture.md` §19.2 currently defines `questions.label` as a single Arabic `text` column. Every
such column becomes a **localised JSONB object**:

```sql
-- one column, all locales, no schema change when a locale is added
label jsonb NOT NULL   -- {"ar":"عدد الغرف","tr":"Oda sayısı","en":"Number of rooms"}
```

Rules:
- **The default locale of the deployment is required; others are optional** and fall back to it. A
  missing translation renders the fallback, never an empty string or a raw key.
- Resolution happens **server-side** when building the form, so the client receives one resolved
  string. Do not ship all three locales to the browser for every label.
- `questions.key` stays a stable machine key and is **never translated** — it is what answers and
  pricing modifiers reference. Translating a key orphans stored answers (`code-standards.md` §25).
- `answers` store the option **`value`**, never its label. Labels change; values must not.
- A `text`/`textarea` answer is free user input in whatever language they typed. It is stored as
  written, never machine-translated, and still passes the contact-info scanner.

Affected tables: `service_categories`, `services`, `addons`, `zones`, `questions` (`label`,
`help_text`, `options[].label`), `notification_templates`, `platform_settings` where a value is
user-visible copy.

## 6. ⚠️ The Turkish case-conversion hazard — treat as a correctness rule

Turkish has four `i` letters: dotted `i`/`İ` and dotless `ı`/`I`. Turkish case mapping is therefore
**not** the same as every other locale's:

- `"I".toLocaleLowerCase('tr')` → `"ı"` (dotless), not `"i"`.
- `"i".toLocaleUpperCase('tr')` → `"İ"` (dotted), not `"I"`.

This has broken OpenSSL, Kotlin's compiler intrinsics, and countless auth systems. It is a
correctness and **security** issue wherever case-folding decides whether two identifiers are equal.

**Rules:**

1. **Never use `toLocaleLowerCase()` / `toLocaleUpperCase()` on an identifier.** Emails, tokens,
   status values, account paths, question `key`s, enum comparisons — all use plain
   `toLowerCase()` / `toUpperCase()`, which are locale-independent in JavaScript, or better, are
   compared without case folding at all.
2. Locale-aware casing is for **display text only**, and only with an explicit locale argument.
3. **In Postgres, `lower()` and `upper()` are collation-dependent.** Do not create the database or
   any text column with a Turkish collation, and do not build a case-insensitive uniqueness index on
   an email using `lower()` under one. Pin identifier columns to a deterministic collation (e.g.
   `COLLATE "C"`) or normalise in application code before storing.
4. Sorting **is** locale-aware and should be — use `ORDER BY ... COLLATE "tr-TR-x-icu"` for
   user-facing lists in Turkish, never for keys.
5. Add a test that round-trips `I`, `ı`, `İ`, `i` through every identifier comparison path.

## 7. Fonts, numerals, and formatting

- **v1 is Turkish first (D57):** `tr` is the primary language of the Turkey launch, so every screen is
  verified in `tr` before `ar` and `en`. The design is drawn in Arabic; `tr` and `en` use the same
  layouts, mirrored by logical properties. Turkish runs longer: check chips, steppers and buttons.
- **Copy workflow (D58):** Arabic comes from the design (simple Modern Standard Arabic); English is
  drafted from the meaning of the design; a translator turns the English into Turkish (owner step S21).
  A Turkish string still awaiting translation is marked as such in the catalogue, never filled with
  machine output.
- **Fonts (D48, verified 2026-10-25 by rendering):** Alexandria (headings, numbers, money) and Cairo
  (body) both cover Arabic and Latin Extended, so every Turkish letter (`ı İ ş Ş ğ Ğ ç Ç ö Ö ü Ü`)
  renders in both. **Cairo has no `₺` glyph**, Alexandria does: amounts and currency signs are always
  set in Alexandria (`ui-tokens.md` §5).
- Arabic renders at a larger optical size than Latin at the same point size — the line heights of the
  type scale in `ui-tokens.md` §5 come from the Arabic design; check them in `tr` and adjust the token,
  never one component.
- **Digits:** store Western Arabic numerals (`0-9`) always. **Display them Western in all three
  locales too (D52, as the design draws them):** format `ar` with `ar-u-nu-latn`, because plain `ar`
  renders Arabic-Indic (`٣٬٢٠٠`). Grouping and currency placement still follow the locale:
  `tr` → `₺3.200`, `en` → `₺3,200`, `ar-u-nu-latn` → Western digits in Arabic order. Never copy the
  mockups' `₺3,200` as a fixed format. The contact scanner must keep detecting **both** digit sets — it
  already handles `٠-٩` and must also handle Turkish-formatted numbers (`.` thousands, `,` decimal).
- **Money is formatted, never computed, in the UI** — unchanged. Format with the locale and the
  **row's** currency — read from `regions.currency` for that request or provider, never from a global:
  `Intl.NumberFormat(locale, {style:'currency', currency: row.currency})`.
- Money stays **LTR-isolated** inside RTL text with tabular figures (`ui-rules.md` §21). Same for
  phone numbers and dates.
- Dates: store UTC, format per locale. Both regions use the Gregorian calendar for scheduling; do not
  introduce Hijri without an explicit decision.

## 9. Testing

- Every screen checked in `ar` (RTL) **and** `tr` (LTR). A screen correct in one direction is not done.
- Playwright MCP is configured for exactly this; drive it per locale.
- Assert no hardcoded user-facing string ships in a component (lint rule or grep gate in CI).
- Assert every message key exists in all three files — a missing key must fail the build, not render
  a raw key to a customer.
- Turkish identifier round-trip test (§6.5).
- Pseudo-locale or longest-string test: German-length or Turkish compound words overflow layouts that
  Arabic did not.
